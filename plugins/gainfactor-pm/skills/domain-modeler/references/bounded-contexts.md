# 业务模型的适用边界与协作关系

业务模型适用边界（Bounded Context，行业常称“限界上下文”）是语言和模型保持一致的范围。模型协作关系（Context Mapping，行业常称“上下文映射”）记录不同模型之间的组织关系、依赖方向和转换方式。

## 划分边界

- 找出同一词具有不同含义的区域。
- 找出规则、生命周期和数据所有权由不同责任方维护的区域。
- 检查哪些能力可以独立变化，哪些必须协同变化。
- 先记录现状，再提出目标边界；遗留系统可能暂时是边界混乱的“大泥球（Big Ball of Mud）”。

业务模型适用边界不等于微服务、代码模块、团队或部署单元。团队边界经常影响模型边界，但不能直接用组织结构替代领域分析。

## 九种常见关系

| 模式 | 含义与使用条件 |
|---|---|
| Partnership（共同演进） | 两个团队共同计划并同步调整相互依赖的模型 |
| Shared Kernel（共享内核） | 共同维护一小块共享模型，变更需要双方同意 |
| Customer–Supplier（客户—供应商） | 上游提供能力，下游需求进入协商和计划 |
| Conformist（下游接受上游模型） | 下游缺少影响力，选择直接适配上游模型 |
| 外部模型转换层（Anti-Corruption Layer, ACL，行业称“防腐层”） | 用转换层保护本地模型，不让外部概念渗入 |
| 开放主机服务（Open Host Service, OHS） | 上游提供稳定、通用的访问协议 |
| 发布语言（Published Language） | 双方通过公开且版本化的 schema 或协议通信 |
| Separate Ways（各自独立） | 集成成本高于收益，双方不直接集成 |
| Big Ball of Mud（大泥球） | 边界混乱的遗留模型，只能隔离并逐步治理 |

## 上下文图要求

每个上下文写清名称、职责、非职责、语言、所有者和数据所有权。每条关系写清上下游、关系模式、转换位置、变更协商方式和失败风险。

Mermaid 图只展示结构；正文必须解释为什么选择该边界与关系。不要为了使用 DDD 而给每条线套模式名称。
