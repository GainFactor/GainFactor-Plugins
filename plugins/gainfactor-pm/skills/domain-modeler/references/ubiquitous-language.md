# 团队共同使用的业务语言

团队共同使用的业务语言（Ubiquitous Language，行业常称“通用语言”）不是项目结束后补写的术语表，而是业务人员与研发在对话、文档、代码、测试和图示中持续使用的共同语言。

## 建立方式

1. 用具体业务场景开始，例如“客户提交索赔后发生什么”，不要先讨论表或接口。
2. 记录业务人员自然使用的名词、动作、状态和限制条件。
3. 追问相似词是否真的相同，例如“审核”“评估”“批准”是否代表不同动作。
4. 用模型名称和操作复述场景，让领域专家纠正。
5. 把确认后的语言应用到文档、类、方法、事件和测试；语言变化时同步重命名。

## 术语表

| 字段 | 内容 |
|---|---|
| 术语 | 当前上下文中的标准名称 |
| 业务定义 | 能判断一个实例是否属于该概念的定义 |
| 适用边界 | 该含义在哪个业务模型适用边界（Bounded Context，行业常称“限界上下文”）内成立 |
| 业务示例 | 领域专家认可的真实用法 |
| 冲突或历史名称 | 同义词、旧名称、其他上下文中的不同含义 |
| 来源 | BRD、访谈、规则、代码或负责人 |

不要收录 Repository、Controller、Redis 等技术词。技术实现可以使用这些词，但它们不是业务语言。

## 代码中的语言

优先使用能表达业务动作的名称：`claim.submitForAdjudication()` 比 `service.process(dto)` 更容易校验。`Manager`、`Helper`、`Processor`、`Utils` 通常说明概念尚未澄清。

同一个词在不同上下文中可以有不同含义。例如“账户”在认证中可能是登录身份，在财务中可能是账务位置。不要强行统一；在边界处明确转换。

## 变化信号

- 对话中频繁出现“差不多”“其实不是这个意思”。
- 代码用 `type` 或大量条件分支区分本应独立的概念。
- 领域专家持续纠正开发者使用的名称。
- 一个类或方法难以用业务语言命名。

这些信号要求回到场景重新建模，而不是增加更多技术抽象。
