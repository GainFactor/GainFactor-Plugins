# 已经发生的重要业务事实

已经发生的重要业务事实（Domain Event，行业常称“领域事件”）表达业务人员关心的结果。名称使用过去式，例如 `OrderPlaced`、`ClaimDenied`、`MembershipExpired`。

## 判断是否需要事件

询问：“这个事实发生后，业务中还有谁需要知道或采取行动？”如果它只表示字段被更新，且没有业务意义，通常不需要事件。

事件至少记录：事件 ID、事件类型、发生时间、聚合身份，以及消费者完成业务动作所需的最小事实。事件是不可变事实，不应在发布后修改。

## 领域事件与集成事件

- 领域事件用于一个业务模型适用边界内部，使用该范围内团队共同的业务语言。
- 集成事件（Integration Event）跨上下文或外部系统传播，必须使用发布语言并考虑版本兼容。
- 两者可以转换，但不要把内部一致性单元直接序列化为公共事件。

## 一致性与可靠性

聚合内部保持立即一致；聚合之间通常通过事件实现最终一致性。需要同时写数据库与发布消息时，在 HLD/LLD 中评估事务发件箱（Transactional Outbox）。消费者按事件 ID 实现幂等。

跨多个聚合或服务的长流程可以使用 Saga，但必须先定义真实的业务补偿动作。Saga 不是普通函数调用链的替代名称。

## 事件溯源

事件溯源（Event Sourcing）把事件历史作为事实源，并通过回放得到当前状态。只有以下需求足够重要时才考虑：

- 完整审计和历史状态查询是核心能力。
- 需要按时间重建状态或修正计算逻辑后重新回放。
- 领域天然围绕事件演进，并能承担版本化、迁移和运维复杂度。

使用领域事件不等于必须使用事件溯源。
