# 业务对象、业务值与一致性单元

战术构件用于把业务规则落实到模型。先理解业务身份和一致性要求，再决定类与对象结构。

## 有身份的业务对象与由属性定义的业务值

有持续身份的业务对象（Entity，行业称“实体”）的判断问题是：“即使所有属性都变化，它是否仍是同一个业务对象？”订单、客户或合同通常依靠持续身份区分。

由属性整体定义的业务值（Value Object，行业称“值对象”）没有独立身份，通常不可变。例如金额、地址、日期范围。两个属性相同的业务值在业务上相等。

优先考虑值对象。只有业务确实需要追踪生命周期与身份时才使用实体，不要因为数据库有主键就把所有对象都建成实体。

## 一次业务操作必须共同保持有效的对象

一致性单元（Aggregate，行业称“聚合”）是需要在一次业务操作中共同保持有效的一组业务对象和业务值。唯一修改入口（Aggregate Root，行业称“聚合根”或“根实体”）负责保护这组对象的规则。

设计步骤：

1. 写出始终必须成立的业务规则（Invariant）。
2. 确定哪些对象必须在一次事务中共同变化。
3. 选择能保护这些规则的聚合根。
4. 删除不需要立即一致的对象，让它们成为独立聚合。
5. 跨聚合只保存身份引用，通过领域事件完成后续协作。

## 一致性单元记录表

| 字段 | 说明 |
|---|---|
| 唯一修改入口（Aggregate Root） | 外部执行操作的唯一入口 |
| 内部成员 | 不能绕过聚合根独立修改的对象 |
| 命令 | 业务允许执行的动作 |
| 始终必须成立的业务规则（Invariant） | 每次操作都必须保护的规则 |
| 重要业务事实（Domain Event） | 操作成功后产生的业务事实 |
| 一致性边界 | 立即一致与最终一致的分界 |

## 常见错误做法

- 巨型聚合导致慢加载、并发冲突和事务瓶颈。
- 对象只有 getter/setter，规则全部位于服务中，形成贫血领域模型。
- 聚合之间持有完整对象引用，导致边界失效。
- 使用一个聚合事务维护跨上下文规则，掩盖真实的业务补偿过程。

领域服务（Domain Service）只承载无法自然归属实体或值对象的业务操作；应用服务负责协调，不应成为业务规则仓库。
