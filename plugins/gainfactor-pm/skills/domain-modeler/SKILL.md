# Domain Modeler

> **语言规则**：默认跟随用户输入语言。面向业务读者时先说明概念解决什么问题，首次出现专业术语时使用“白话业务含义（English Term，行业常称‘中文术语’）”；代码标识符、英文事件名、API 字段和 `TRACEABILITY-METADATA` 保持原文。详见 `../../references/language-policy.md`。

通过领域驱动设计（Domain-Driven Design, DDD）让软件模型反映真实业务。目标不是套用 DDD 名词，而是让业务人员和研发能用同一套概念解释真实场景、规则、边界和协作。

## 角色与边界

本 Skill 是**产物编写型**，采用“证据 → 场景与语言 → 战略边界 → 战术模型 → 评分挑战 → 正式交付”的线性阶段；在 Phase 1–4 内嵌有限访谈循环。

- 可以由 BRD 的 `Domain Modeling Handoff` 发起，也可以在 PRD 前独立发起；没有 PRD 不构成阻断。
- 领域建模按业务复杂度触发，不是主流程硬门禁；没有复杂规则、语言冲突或模型边界问题时可以明确跳过。
- 可以在 PRD、API、HLD 或实现阶段补做或修订，但新证据与已批准基线冲突时必须显式确认。
- 不替代 BRD 定义业务目标，不替代 PRD 定义需求范围，不决定 API、数据库、微服务、部署或技术选型。
- 简单 CRUD、纯部署设计、数据库字段设计和一般技术选型通常跳过。
- 不为了提高分数强行引入一致性单元、事件、读取与保存接口或复杂模式。

## 输入与证据优先级

输入可以是 BRD、业务流程、访谈记录、领域专家说明、组织职责、现有代码、API、已有 PRD 或旧领域模型。发生冲突时按以下顺序处理：

1. 用户在本轮明确确认的业务决定；
2. 已批准的 BRD、领域模型或其他正式业务基线；
3. 可追溯的领域专家说明和真实业务规则；
4. 现行系统、代码和 API 所反映的事实；它们证明“现在怎样”，不自动证明“业务应该怎样”；
5. 草稿、历史材料和未确认访谈；
6. 推断与建议，必须明确标记，不能冒充事实。

关键术语含义、始终必须成立的业务规则、业务模型边界、数据所有权或核心域归属缺少证据时，进入访谈循环；每轮只问 2–3 个会改变模型的问题。用户无法确认时记录为未决项，不能静默固化进正式基线。

## 核心原则

**模型进入代码，代码反映模型。** 团队共同确认的业务语言应进入讨论、文档、代码和测试；术语或规则变化时，模型与代码映射也需要更新。

## 执行进度清单

使用宿主计划机制维护状态；没有专用机制时按以下清单推进。每完成一个 Phase 立即记录中间产物和未决项。暂停后从最早未满足的 Exit Criteria 恢复，不默认从头开始。

```text
□ Phase 0：确认建模任务、范围与证据
□ Phase 1：还原关键业务场景与共同语言
□ Phase 2：识别业务能力、模型边界与协作关系
□ Phase 3：设计业务对象、一致性规则与重要业务事实
□ Phase 4：完成 7+3 评分、反例挑战与用户确认

□ Phase 6：验证、发布并交接下游
```

## 六段分析框架与按需参考

六段框架是每次建模都要检查的分析视角，不是六个可以随意换序的执行阶段。不适用项必须说明原因。

### 1. 团队共同使用的业务语言（Ubiquitous Language，行业常称“通用语言”）

从真实场景提取名词、动作、状态和规则。同一个词在不同边界可以有不同含义；不要用 `Manager`、`Helper`、`Processor` 掩盖未澄清概念。梳理术语或代码命名时完整读取 [团队共同使用的业务语言](references/ubiquitous-language.md)。

### 2. 业务模型的适用边界与协作关系

业务模型适用边界（Bounded Context，行业常称“限界上下文”）说明某套语言和模型在哪里成立；模型协作关系（Context Mapping，行业常称“上下文映射”）说明不同模型怎样协作和转换。划分边界时完整读取 [业务模型的适用边界与协作关系](references/bounded-contexts.md)。

### 3. 业务对象、业务值与一致性单元

有持续身份的业务对象（Entity，行业称“实体”）即使属性变化仍是同一对象；由属性整体定义的业务值（Value Object，行业称“值对象”）通常不可变。一致性单元（Aggregate，行业称“聚合”）保护一次业务操作后必须共同有效的对象；唯一修改入口（Aggregate Root，行业称“聚合根”或“根实体”）保护始终必须成立的业务规则（Invariant）。设计战术模型时完整读取 [业务对象、业务值与一致性单元](references/building-blocks.md)。

### 4. 已经发生的重要业务事实

已经发生的重要业务事实（Domain Event，行业称“领域事件”）表达业务人员关心的结果，例如 `OrderPlaced`，而不是 `RecordUpdated`。定义事件与最终一致性时完整读取 [已经发生的重要业务事实](references/domain-events.md)。

### 5. 领域对象的保存、创建与业务条件表达

领域对象的读取与保存接口（Repository，行业称“仓储”）隐藏数据库与 ORM，这里的“仓储”不是物流仓库。复杂业务对象的创建规则（Factory，行业称“工厂”）保护复杂创建过程；可复用、可组合的业务判断条件（Specification，行业称“规约”）表达领域判断。只有出现相应复杂度时才完整读取 [领域对象的保存、创建与业务条件表达](references/repositories-factories.md)。

### 6. 识别核心业务能力并分配投入

核心域（Core Domain）形成业务差异；支撑子域对业务必要但不是主要差异；通用子域优先采购或复用成熟能力。做能力分类和投入判断时完整读取 [识别核心业务能力并分配投入](references/strategic-design.md)。

## Phase 0：确认建模任务、范围与证据

**Goal**：确认为什么要建模、模型覆盖什么，以及谁有权确认业务含义。

**Inputs**：用户请求、`Domain Modeling Handoff`（如有）、已有材料和工作区现状。

**Actions**

1. 判断触发信号是否真实存在：术语冲突、复杂规则、生命周期、模型边界、数据所有权、外部模型转换或核心域不清。
2. 冻结 `{subject-slug}`，确定建模范围、明确不建模的范围和下游消费者。
3. 建立证据清单，区分已批准事实、现行实现、领域专家说明、草稿、推断和未知。
4. 识别可确认业务含义的领域专家或决策人。

**Intermediate Deliverable**：建模任务卡，包括触发原因、范围/非范围、证据表、参与者、目标下游和未决问题。

**Exit Criteria**：范围和至少一个关键业务场景明确；关键证据有来源；能识别谁负责确认业务含义。

**Stop / Escalation**：无法确定主体、范围或任何可验证业务场景时停止。若确认只是简单 CRUD 或纯技术问题，记录 `not_needed` 并退出，不生成伪领域模型。

**Resume**：回读任务卡，从缺失的范围、证据或确认人继续。

## Phase 1：还原关键业务场景与共同语言

**Goal**：用业务人员能校验的场景建立共同语言，而不是从数据表或类名开始。

**Inputs**：Phase 0 任务卡和 [团队共同使用的业务语言](references/ubiquitous-language.md)。

**Actions**

1. 选取能覆盖正常路径、规则冲突和失败/补偿的关键业务场景。
2. 记录参与者、触发、业务动作、状态变化、必须成立的规则和结果。
3. 建立术语表，记录定义、适用边界、例子、同义/冲突词和来源。
4. 对会改变规则或边界的术语冲突，每轮询问 2–3 个问题；每轮结束总结已确认、假设和未决项。
5. 请用户或领域专家确认关键场景与高影响术语，不要求确认排版形式。

**Intermediate Deliverable**：关键场景表、术语表、冲突清单和确认记录。

**Exit Criteria**：每个核心术语能用真实场景解释；高影响冲突已确认或明确保留为阻断未决项。

**Stop / Escalation**：关键术语仍有互斥含义且无法确定适用边界时，不进入战术模型。低影响缺口可标记待验证后继续。

**Resume**：从冲突清单中最早未确认的术语或场景继续，保留已确认词汇。

## Phase 2：识别业务能力、模型边界与协作关系

**Goal**：明确哪些能力形成业务差异、每套模型在哪里有效，以及边界之间如何协作。

**Inputs**：Phase 1 场景与术语；[识别核心业务能力并分配投入](references/strategic-design.md)；[业务模型的适用边界与协作关系](references/bounded-contexts.md)。

**Actions**

1. 按核心域、支撑子域、通用子域分类业务能力，并记录业务理由，不按技术复杂度分类。
2. 根据语言含义、规则、生命周期、数据所有权和变化节奏提出当前边界与目标边界。
3. 为每个边界记录职责、非职责、语言、所有者和数据所有权。
4. 为每条协作关系记录上下游、转换位置、变更协商和失败风险；外部模型进入核心前需要时建立外部模型转换层（Anti-Corruption Layer, ACL，行业称“防腐层”）。
5. 使用 Mermaid 绘制关系图，并用正文解释关键决策。
6. 对核心域归属、边界拆合和数据所有权等高影响选择请求用户确认。

**Intermediate Deliverable**：能力分类表、边界清单、模型协作关系图、决策记录和未决边界。

**Exit Criteria**：核心能力有业务依据；每个边界有职责与所有权；关键关系能说明转换和失败处理。

**Stop / Escalation**：边界只按组织、数据库或微服务划分，或核心域归属仍有冲突时，回到场景与语言，不继续设计一致性单元。

**Resume**：从未决边界或受影响的业务场景继续；不重做无关边界。

## Phase 3：设计业务对象、一致性规则与重要业务事实

**Goal**：把已确认的语言和边界落实为能保护业务规则的模型，但不越界决定技术实现。

**Inputs**：Phase 2 边界；[业务对象、业务值与一致性单元](references/building-blocks.md)；[已经发生的重要业务事实](references/domain-events.md)。出现复杂持久化、创建或判断条件时再读取 [领域对象的保存、创建与业务条件表达](references/repositories-factories.md)。

**Actions**

1. 在每个边界内识别有身份的业务对象与由属性定义的业务值。
2. 先写始终必须成立的业务规则，再确定一次业务操作必须共同变化的对象和唯一修改入口。
3. 保持一致性单元小而明确；跨单元只保存身份引用，明确立即一致、最终一致和业务补偿。
4. 记录命令、状态变化和已经发生的重要业务事实；区分内部领域事件和跨边界集成事件。
5. 只有复杂度真实存在时设计 Repository、Factory 或 Specification；不得把数据库表、ORM、API 或消息中间件写成业务模型结论。
6. 用 Phase 1 关键场景逐条走查模型，寻找绕过规则、巨型聚合、贫血模型和外部概念泄漏。

**Intermediate Deliverable**：业务对象/业务值清单、一致性单元记录表、规则清单、事件目录、场景走查和代码映射建议。

**Exit Criteria**：每条关键规则有明确保护者；每个重要状态变化能回到业务场景；跨边界协作不泄漏内部模型。

**Stop / Escalation**：无法给规则指定所有者、一个一致性单元包含多个独立生命周期，或模型只能用数据库/接口术语解释时，回到 Phase 1 或 Phase 2。

**Resume**：从失败场景对应的规则、边界或一致性单元继续，局部返工。

## Phase 4：完成 7+3 评分、反例挑战与用户确认

**Goal**：用固定 10 项标准暴露模型缺口，而不是用分数装饰报告。

**Inputs**：Phase 1–3 全部中间产物及其证据。

**Actions**

1. 对下面 7 项快速诊断和 3 项模型深度逐项给 `0/1`，记录证据与修正建议；证据不足计 0，不默认得分。
2. 使用至少一个失败、取消、补偿或并发冲突场景挑战模型。
3. 汇总高影响边界、规则和未决项，请用户确认模型基线；用户确认业务决定，不确认 DDD 名词本身。

**Intermediate Deliverable**：10 项评分表、反例挑战记录、确认结果和修正清单。

**Exit Criteria**：10 项全部有证据或缺口说明；反例已处理或列为未决；核心业务决定已确认。

**Stop / Escalation**：存在会改变核心术语、边界或规则所有者的未决项时，不把文档标为已确认；可以交付 `draft` 并明确阻塞。

**Resume**：从最低分且会影响下游的项目继续；不要为了提高总分重做不相关部分。

## 评分：10 分制（固定 7+3 合同）

先使用“快速诊断”的 7 项，每项满足得 1 分；再评估 3 项模型深度，每项满足得 1 分。不得调整项目数量、合并项目或用总分掩盖单项缺口。

### 7 项快速诊断

| # | 白话检查问题 | 对应 DDD 术语 |
|---:|---|---|
| 1 | 业务人员是否能读懂模型中的名称和动作？ | Ubiquitous Language |
| 2 | 每套业务模型在哪个范围内有效是否明确？ | Bounded Context / Context Mapping |
| 3 | 一组对象能否在一次业务操作后保持有效，并且存在唯一修改入口？ | Aggregate / Aggregate Root / Invariant |
| 4 | 业务对象是否包含真实业务行为，而不只是保存数据？ | Rich Domain Model / Entity / Value Object |
| 5 | 跨一致性单元的协作是否通过重要业务事实传递？ | Domain Event |
| 6 | 外部系统的数据进入本地前是否先转换成自己的业务模型？ | Anti-Corruption Layer (ACL) |
| 7 | 是否已识别最值得投入的核心业务能力？ | Core Domain / Subdomain |

### 3 项模型深度

| # | 白话检查问题 | 对应 DDD 术语 |
|---:|---|---|
| 8 | 每条始终必须成立的业务规则是否都有明确保护者，并经过失败场景验证？ | Invariant Ownership / Aggregate Design |
| 9 | 模型边界之间的依赖、数据所有权、转换位置和失败风险是否明确？ | Context Mapping / Published Language / ACL |
| 10 | 文档、代码和测试是否能沿用同一语言，并能追溯到场景、规则与业务事实？ | Model–Code Alignment / Traceability |

正式评分表必须包含：`白话检查问题 | 对应 DDD 术语 | 得分 | 证据 | 未通过时的修正建议`。

| 白话检查问题 | 对应 DDD 术语 | 得分 | 证据 | 未通过时的修正建议 |
|---|---|---:|---|---|
| 按上述 10 项逐行填写 | 填写对应术语 | 0/1 | 填写来源或说明证据不足 | 填写可执行修正动作 |

评分解释：

- **9–10 分**：模型可作为稳定业务基线，下游仍需遵守未决项和版本边界；
- **7–8 分**：主体可用，但存在明确的局部修正项；
- **4–6 分**：已形成部分共同语言，关键边界或规则仍不稳定；
- **0–3 分**：技术化命名、全局单一模型或规则分散，不能作为可靠基线。

分数不是发布门槛。即使总分较高，只要核心术语、边界或规则所有权存在阻断未决项，也只能交付 `draft`。

## Phase 5：形成正式领域模型文档

**Goal**：将已确认结果写成业务人员可读、研发可消费且脱离对话也完整的正式文档。

**Inputs**：Phase 0–4 中间产物、确认记录和修正结果。

**Actions**

1. 写入 `docs/gainfactor/{subject-slug}/domain-model.mdx`，稳定 artifact key 为 `domain-model`。
2. 前半部分使用白话标题，至少包含范围与证据、共同语言、业务能力分类、模型边界、协作关系图、业务对象/业务值/一致性单元、重要业务事实、10 项评分和未决问题。
3. 后半部分面向 API/HLD/LLD 交接，保留标准 DDD 术语、代码映射和集成边界；不生成具体 API、数据库或部署方案。
4. 所有关键结论关联来源；推断、建议、现行实现和已确认业务决定保持可区分。

**Intermediate Deliverable**：可独立阅读的 `domain-model.mdx` 草稿及来源/未决项检查结果。

**Exit Criteria**：六段框架均已检查；10 项评分完整；关键决策可追溯；业务与技术交接边界清楚。

**Stop / Escalation**：无法冻结 `{subject-slug}` 或正式文档与用户已确认决定冲突时停止写入并请求确认。

**Resume**：从受影响章节和来源记录继续，不重新推导已确认内容。

## Phase 6：验证、发布并交接下游

**Goal**：验证文档内容与交付链路，并让下游能稳定消费。

**Inputs**：Phase 5 正式草稿、插件发布能力和下游契约。

**Actions**

1. 检查术语一致、边界关系、规则所有者、事件命名、10 项评分、来源和未决项。
2. 检查 Mermaid 能渲染、内部锚点有效、无未注册组件；图不能代替决策说明。
3. 调用 `$document-publisher` 的 `artifact-management` 与 `publishing/publish` 创建或更新默认门户。
4. 回读稳定路由，确认标题、核心术语、边界图、规则、事件、评分和未决项已落盘；发布失败时保留源文档并报告阻断。
5. 向 BRD、User Journey、PRD、API、HLD 和 LLD 交接稳定语言、边界、规则、事件和未决项；下游不得静默改写。

**Intermediate Deliverable**：内容检查记录、发布结果和下游交接摘要。

**Exit Criteria**：源文档存在且可读；发布成功并回读，或发布失败已准确报告且源文档保留；下游消费字段明确。

**Stop / Escalation**：内容验证失败时不发布；门户失败时不宣称门户已更新。用户明确要求仅聊天输出或禁止写文件时，才跳过文件与门户，并说明交付降级。

**Resume**：内容失败回到对应 Phase；发布失败从已保留的源文档重试，不重新建模。

## 常见错误做法

| 错误 | 问题 | 修正方向 |
|---|---|---|
| 用技术名称代替业务语言 | 领域专家无法校验模型 | 改成业务认可的概念和动作 |
| 整个系统共用一个模型 | 同一术语承载冲突含义 | 划分业务模型适用边界并定义转换 |
| 一致性单元过大（巨型聚合） | 并发冲突、事务边界不清 | 拆小、按身份引用、接受最终一致 |
| 业务对象只存数据（贫血领域模型） | 规则散落在服务 | 把业务行为和必须成立的规则放回模型 |
| 外部模型直接进入核心业务模型 | 被供应商或遗留概念绑架 | 建立外部模型转换层（ACL） |
| 把业务模型适用边界等同微服务 | 过早引入分布式复杂度 | 先确定模型边界，再决定部署 |
| 跳过领域专家或确认点 | 执行者自行发明业务模型 | 用真实场景持续校正语言与规则 |

## 完成标准与下游契约

- 六段框架均已检查；不适用项写明原因。
- 7+3 评分逐项有证据和修正建议，没有为了达到 10 分强行引入模式。
- 关键术语、边界、规则、跨边界关系和未决项能追溯到业务证据。
- BRD、User Journey 和 PRD 可以引用领域模型；API、HLD 与 LLD 在模型存在时复用稳定语言、边界、规则和事件。
- 新证据与模型冲突时显式提出变更，不静默覆盖；领域模型是可演进基线，不是永久真理。
