# 中文产品术语表

本术语表统一产品经理在研究、需求、界面、后台、账号权限和运营协作中常用的语言。它解释产品工作中的约定含义，不收录高层设计、防腐层、严重度等纯技术设计或质量管理术语，也不替代具体项目的业务术语表。

术语定义解决“一个词是什么意思”；PRD 中如何把抽象概念写成具体的页面、信息和操作，见[中文产品语言规范](product-language-guide.md)。

## 使用规则

- 首次使用缩写时写出中文全称与英文原文，例如“产品需求文档（Product Requirements Document，PRD）”。
- 同一产物只使用一个标准名称；历史名称或近义词仅用于检索，不混用。
- 项目特有术语应写入对应产品的领域模型，并注明适用边界；不要把局部含义扩展为全局定义。
- 定义发生变化时，同时检查相关文档、代码、测试和追溯关系。

## 产品研究与决策

| 标准术语 | 英文 / 缩写 | 定义 | 使用边界与易混概念 |
|---|---|---|---|
| 产品 | Product | 为特定用户持续解决一类问题，并通过明确机制创造价值的能力组合。 | 不等同于单个功能、项目或一次性交付物。 |
| 产品定义 | Product Definition | 对产品定位、目标用户、核心价值、责任边界、生命周期和商业模式形成的稳定基线。 | 回答“产品是什么、为谁服务、为何存在”，不展开详细需求或技术实现。 |
| 产品愿景 | Product Vision | 对产品希望创造的长期用户价值和未来状态的方向性描述。 | 提供长期方向，不等同于阶段目标、路线图或宣传口号。 |
| 产品策略 | Product Strategy | 为实现产品愿景，对目标市场、用户、价值、差异化和关键取舍作出的选择。 | 说明如何竞争和取舍，不等同于功能计划或项目排期。 |
| 产品定位 | Product Positioning | 产品针对特定用户和场景所选择的价值位置及差异化表达。 | 不等同于宣传口号；应能约束目标用户、场景和取舍。 |
| 目标用户 | Target User | 产品优先服务、且其问题与价值假设需要被验证的人群。 | 是一个可识别群体，不是虚构的单一人物。 |
| 用户分群 | User Segmentation | 按行为、需求、场景或价值差异划分用户群体的方法及结果。 | 不应只按年龄、性别等人口属性机械划分。 |
| 用户画像 | User Persona | 基于证据对某一用户群体的代表性角色、目标、行为和约束进行结构化描述。 | Persona 是群体代表，不是真实用户档案，也不是目标用户本身。 |
| 用户场景 | User Scenario | 用户在特定情境下，为完成目标而与产品发生交互的具体背景。 | 强调情境、触发和目标，不等同于页面或功能清单。 |
| 用户任务 | Job to Be Done, JTBD | 用户在某种情境下希望取得的进展或完成的事情。 | 关注用户要达成的结果，不限定为当前产品中的操作。 |
| 价值主张 | Value Proposition | 产品为目标用户解决什么问题、带来什么收益，以及为何值得选择的可验证陈述。 | 不等同于功能列表或品牌口号。 |
| 竞品 | Competitor | 与本产品争夺同一用户需求、预算、时间或流程位置的替代方案。 | 包括直接、间接和潜在竞品；“同赛道”不自动构成竞品。 |
| 竞品分析 | Competitive Analysis | 围绕明确产品决策，对竞品、替代关系、能力、体验和证据进行比较并形成取舍建议。 | 不是资料汇编；未知或未测试的能力不能当作不存在。 |
| 假设 | Hypothesis | 尚未被充分证据确认、但可以通过观察或实验验证的判断。 | 必须与事实和已确认决定区分。 |
| 用户痛点 | User Pain Point | 用户在完成目标时反复遇到、并造成时间、成本、风险或情绪损失的问题。 | 不等同于用户提出的功能要求；应说明发生场景和影响。 |
| 产品机会 | Product Opportunity | 基于用户问题、市场变化或现有能力识别出的潜在价值空间。 | 机会不是已批准需求，需要继续验证价值、可行性和优先级。 |
| 最小可行产品 | Minimum Viable Product, MVP | 用最小范围验证关键价值与高风险假设的可交付产品版本。 | “最小”指验证闭环最小，不等同于低质量版本或功能阉割版。 |
| 路线图 | Product Roadmap | 按目标、价值和依赖表达产品演进方向的计划。 | 不等同于精确到日期的项目排期或功能许愿清单。 |

## 指标与验证

| 标准术语 | 英文 / 缩写 | 定义 | 使用边界与易混概念 |
|---|---|---|---|
| 产品指标 | Product Metric | 用于观察产品价值、用户行为或业务结果的可计算量。 | 指标必须包含口径、数据来源、时间窗口和责任人。 |
| 北极星指标 | North Star Metric, NSM | 最能代表产品为用户持续创造核心价值的产品级指标。 | 通常不直接等同于收入、活跃用户数或某个单次任务指标。 |
| 主要指标 | Primary Metric | 针对当前产品任务或决策，最直接衡量目标是否达成的指标。 | 范围可以小于北极星指标；一个任务应明确唯一主指标。 |
| 驱动指标 | Driver Metric | 对主要指标具有可解释影响、可通过产品行动改变的前置指标。 | 相关性不自动证明因果关系。 |
| 过程指标 | Process Metric | 反映用户旅程或业务流程中间步骤表现的指标。 | 用于定位变化，不应取代最终价值结果。 |
| 底线指标 | Guardrail Metric | 防止优化主要指标时损害质量、安全、成本或其他关键利益的约束指标。 | 这里的 Guardrail Metric 是指标约束，不等同于项目级工程规范。 |
| 指标口径 | Metric Definition | 对指标的计算公式、统计对象、事件、去重规则、时间窗口和例外情况的完整约定。 | 只有指标名称而没有口径，不能支持跨团队比较。 |
| 基线 | Baseline | 在变更或实验前，用于比较的当前表现或已批准版本。 | 指标基线是数值参照；文档基线是已批准的内容版本。 |
| 验收标准 | Acceptance Criteria | 判断一项需求是否满足预期、且能够被测试验证的条件集合。 | 不等同于实现步骤或测试用例；它描述可观察结果。 |
| 获客 | Acquisition | 让新的目标用户首次接触并进入产品的过程。 | 不等同于注册；获客应注明渠道、目标人群和进入产品的判定点。 |
| 激活 | Activation | 新用户首次完成能够体现产品核心价值的关键行为。 | 不等同于注册、登录或打开页面；激活行为应按产品价值单独定义。 |
| 参与度 | Engagement | 用户使用产品关键能力的频率、深度或质量。 | 不等同于停留时长；需要结合产品价值定义关键行为。 |
| 留存 | Retention | 一组用户在经过指定时间后仍返回并完成约定有效行为的情况。 | 必须说明用户群、起算事件、返回行为和时间窗口。 |
| 流失 | Churn | 原有用户在指定时间窗口内停止使用、取消服务或不再产生约定价值行为的情况。 | 不是留存率的简单口语反义词；应单独定义流失事件和观察窗口。 |
| 转化 | Conversion | 用户完成某个预先定义目标行为的结果。 | 注册、提交、购买或升级都可能是转化，使用时必须明确目标行为。 |
| 转化率 | Conversion Rate | 在符合条件的起始人群中，完成目标行为的人数或次数占比。 | 必须写清分子、分母、去重规则和转化窗口。 |
| 转化漏斗 | Conversion Funnel | 按顺序描述用户从起点到目标行为所经历的关键步骤及各步转化情况。 | 是分析模型，不代表所有用户都必须遵循唯一线性路径。 |
| 流失节点 | Drop-off Point | 在用户流程或转化漏斗中，用户未继续进入下一关键步骤的位置。 | 只能说明流失发生在哪里，不能单独证明流失原因。 |
| 用户群组 | Cohort | 按共同属性、起始时间或行为条件划分、用于比较表现的一组用户。 | 行业常称“同期群”；不等同于长期固定的用户分群。 |
| 功能采用 | Feature Adoption | 用户开始并持续使用某项功能以获得其预期价值的过程。 | 不等同于功能曝光或单次点击。 |
| 活跃用户 | Active User | 在指定时间窗口内完成约定有效行为的去重用户。 | 必须定义有效行为和身份去重口径，不能仅凭登录判定。 |
| 日活跃用户 | Daily Active Users, DAU | 一天内满足活跃用户定义的去重用户数。 | “一天”的时区和有效行为口径必须明确。 |
| 周活跃用户 | Weekly Active Users, WAU | 连续或自然一周内满足活跃用户定义的去重用户数。 | 必须说明采用自然周还是滚动七天。 |
| 月活跃用户 | Monthly Active Users, MAU | 连续或自然一个月内满足活跃用户定义的去重用户数。 | 必须说明采用自然月还是滚动三十天。 |

## 需求与体验

| 标准术语 | 英文 / 缩写 | 定义 | 使用边界与易混概念 |
|---|---|---|---|
| 业务需求文档 | Business Requirements Document, BRD | 描述业务问题、目标、范围、价值、约束和关键业务规则的基线文档。 | 重点是业务为何需要改变，不规定完整产品方案或技术实现。 |
| 产品需求文档 | Product Requirements Document, PRD | 描述产品要解决什么问题、为谁解决、提供什么能力及如何验收的需求基线。 | 主要回答 What 和 Why；API、数据库和部署方案属于技术设计。 |
| 用户旅程 | User Journey | 用户从触发到达成目标的端到端步骤、决策、状态与异常路径。 | 不等同于单页流程图；应覆盖正常、失败和恢复路径。 |
| 用户流程 | User Flow | 用户在产品中完成某项具体任务所经过的页面、操作和分支路径。 | 范围通常小于用户旅程；用户旅程还可包含跨渠道体验、情绪和触点。 |
| 首次使用引导 | Onboarding | 帮助新用户理解产品并尽快完成首次关键价值行为的体验过程。 | 不等同于注册流程、功能教程或一次性弹窗。 |
| 线框图 | Wireframe | 在视觉细节确定前，用于表达页面结构、内容层级和主要功能的低细节界面草图。 | 不等同于视觉稿或可交互原型。 |
| 用例 | Use Case | 一个参与者为实现目标，与系统进行的一组有边界的交互。 | 用例比单条需求更接近行为流程，不等同于测试用例。 |
| 边界情况 | Edge Case | 只在输入、状态、时间、权限或依赖处于极端或少见条件时出现的情形。 | “低频”不代表可忽略；是否处理取决于影响和风险。 |
| 功能需求 | Functional Requirement | 产品必须提供的行为、能力或业务规则。 | 描述系统应做什么，不包含性能、安全等质量约束。 |
| 非功能需求 | Non-functional Requirement, NFR | 对性能、可靠性、安全性、可用性、兼容性等质量属性的要求。 | 应可度量或验证，不能只写“高性能”“易用”。 |
| 范围 | Scope | 本次产品工作明确包含的目标、用户、场景和能力边界。 | 应同时声明不在范围内的内容，防止隐性扩张。 |
| 原型 | Prototype | 用于验证信息架构、交互流程或视觉方案的可体验表达。 | 不等同于生产实现；高保真也不代表已满足工程质量。 |
| 可用性 | Usability | 特定用户在特定场景中有效、高效且满意地完成目标的程度。 | 不等同于功能“能运行”或界面“好看”。 |

## 需求规划与交付

| 标准术语 | 英文 / 缩写 | 定义 | 使用边界与易混概念 |
|---|---|---|---|
| 用户故事 | User Story | 从用户角色、目标和价值出发，对一项产品需要进行的简短描述。 | 不等同于完整需求；业务规则和可验收条件仍需补充。 |
| 需求池 | Product Backlog | 按当前认知记录并排序的产品需求、问题、改进和探索事项集合。 | 敏捷团队也称“产品待办列表”；它持续演进，不等同于已承诺排期。 |
| 史诗 | Epic | 围绕较大用户目标组织、需要拆分为多个用户故事或需求项的工作单元。 | 不同团队粒度可能不同，不应仅凭工作时长机械判断。 |
| 需求优先级 | Requirement Priority | 基于用户价值、业务影响、风险、成本和依赖等因素确定的相对处理顺序。 | 不等同于问题严重度或明确发布日期。 |
| 发布版本 | Release | 作为一个整体向目标用户交付的一组功能、修复和变更。 | 不等同于迭代；一个发布版本可以跨多个迭代完成。 |
| 版本号 | Version Number | 用于识别某次产品、接口或文档版本的编号。 | 版本号用于标识，不自动代表发布时间、兼容性或内容范围。 |
| 迭代 | Iteration | 在限定周期内完成分析、设计、交付和反馈的一轮产品研发活动。 | 不等同于版本；一次迭代可以不发布，一个版本也可能跨多个迭代。 |

## 产品形态与使用端

| 标准术语 | 英文 / 缩写 | 定义 | 使用边界与易混概念 |
|---|---|---|---|
| 前台 | User-facing Frontend | 直接面向最终用户、承载核心使用旅程的产品界面。 | “前台”描述服务对象，不等同于前端技术；可包括网页、App 或小程序。 |
| 管理后台 | Admin Console | 供管理员配置产品、管理成员、权限、数据和系统级规则的内部界面。 | 不等同于所有内部工具；若主要服务运营人员，应优先称“运营后台”。 |
| 运营后台 | Operations Console | 供运营人员执行内容、活动、用户触达、审核和业务处理的内部界面。 | 与管理后台的区别在使用角色和任务，而不是页面样式。 |
| 商家后台 | Merchant Console | 供商家管理商品、订单、营销、结算和门店等经营活动的产品界面。 | 商家是外部业务用户时，它仍属于用户侧产品，不应笼统称为内部后台。 |
| 工作台 | Workspace / Workbench | 围绕某一角色的高频任务集中展示待办、数据和快捷操作的工作入口。 | 不等同于首页；首页可以承担导航或信息展示，工作台强调任务处理。 |
| 控制台 | Console | 面向专业用户集中提供资源状态、配置和操作能力的产品界面。 | 常用于开发者或系统管理场景；不要与管理后台无差别混用。 |
| 客户端 | Client | 用户直接安装或访问、并与服务端交互的产品形态。 | 可指桌面端、移动端或网页端；使用时应明确具体平台。 |
| 移动端 | Mobile | 面向手机或平板使用场景的产品端。 | 可包含原生 App、移动网页和小程序，需求中应进一步注明。 |
| Web 端 | Web | 通过浏览器访问的产品端。 | 不自动等同于桌面端，也不说明是否适配移动浏览器。 |
| 小程序 | Mini Program | 运行在特定超级应用平台内、受其能力与规则约束的轻量产品形态。 | 不等同于移动网页或原生 App。 |

## 信息架构与页面

| 标准术语 | 英文 / 缩写 | 定义 | 使用边界与易混概念 |
|---|---|---|---|
| 信息架构 | Information Architecture, IA | 对产品内容、功能、层级、分类和导航关系的组织方式。 | 不等同于页面视觉布局或技术架构。 |
| 导航 | Navigation | 帮助用户识别当前位置并到达目标内容或功能的路径机制。 | 菜单是导航的一种实现，不代表导航的全部。 |
| 面包屑导航 | Breadcrumb | 按层级展示当前页面及其父级页面，并允许返回上级的导航方式。 | 适合表达层级位置，不替代主要导航或浏览器返回操作。 |
| 首页 | Home Page | 用户进入某一产品或产品端后的主要起始页面。 | 应按角色和任务定义，不默认等同于数据看板或工作台。 |
| 列表页 | List Page | 以重复条目展示一组同类对象，并支持浏览、查找或批量操作的页面。 | 应明确列表对象、默认排序、空状态和可用操作。 |
| 详情页 | Detail Page | 展示单个对象完整信息、状态及相关操作的页面。 | 不等同于编辑页；查看和修改应按权限与任务区分。 |
| 表单 | Form | 收集、校验并提交一组结构化信息的交互单元。 | 不等同于页面；一个页面可以包含多个表单。 |
| 数据看板 | Dashboard | 汇总关键指标、趋势、异常和行动入口的数据观察界面。 | 不是图表堆砌；应服务明确角色和决策。 |
| 搜索 | Search | 用户输入关键词或条件，从较大信息集合中主动查找目标的能力。 | 与筛选的区别在于搜索通常从查询意图出发。 |
| 筛选 | Filter | 按既定字段或条件缩小当前结果集合的能力。 | 不等同于搜索；筛选条件通常可枚举或结构化。 |
| 排序 | Sort | 按选定字段和方向改变结果展示顺序的能力。 | 排序不改变结果集合，只改变先后次序。 |
| 分页 | Pagination | 将较大结果集合分批展示和访问的交互方式。 | 页码、上一页/下一页和滚动加载是不同方案，需求中应明确。 |
| 空状态 | Empty State | 页面或组件没有可展示内容时呈现的状态及下一步引导。 | 应区分首次无数据、筛选无结果和加载失败。 |
| 缺省状态 | Default State | 用户尚未主动配置或操作时，系统预先呈现的内容与行为。 | 不等同于空状态。 |
| 加载状态 | Loading State | 数据或操作结果尚未返回期间呈现的反馈状态。 | 应区分首次加载、局部刷新和提交处理中。 |
| 错误状态 | Error State | 因输入、权限、网络或系统异常导致任务无法按预期继续时的反馈状态。 | 需要说明原因、影响和恢复方式，不能只显示“出错了”。 |
| 标签页 | Tabs | 在同一页面区域内切换多组并列内容、且通常一次只展示一组内容的界面结构。 | 用于同层内容切换，不应代替跨层级页面导航。 |
| 对话框 | Dialog | 覆盖在当前页面之上，用于完成一项关联任务、输入信息或作出决定的临时窗口。 | 模态对话框会阻止用户操作其后的页面；不要与普通详情页混用。 |
| 抽屉 | Drawer | 从页面边缘展开，用于展示补充信息、导航或上下文操作的临时面板。 | 是否阻断主页面操作应明确；不等同于独立页面。 |
| 提示气泡 | Tooltip | 用户聚焦或指向某个界面元素时显示的简短补充说明。 | 不承载完成任务所必需的信息或交互操作。 |
| 轻提示 | Snackbar / Toast | 在操作后短暂显示、通常不打断当前任务的简短反馈。 | 不承载必须阅读的信息；是否自动消失和能否撤销应明确。 |
| 警告提示 | Alert | 为引起注意而展示的重要状态或风险信息。 | 若要求用户立即决定并阻断当前任务，应使用警告对话框并明确可选操作。 |
| 二次确认 | Confirmation | 在高影响、不可逆或容易误触的操作执行前，请用户再次确认意图的交互。 | 不应滥用于低风险操作；可恢复操作优先提供撤销。 |

## 常见页面区域

| 标准术语 | 英文 / 缩写 | 定义 | 使用边界与易混概念 |
|---|---|---|---|
| 全局顶部栏 | Global Header | 位于产品页面顶部，承载全局品牌、导航、搜索、账号或跨页面操作的区域。 | 作用范围跨页面，不等同于当前页面的标题区。 |
| 侧边导航 | Side Navigation | 位于页面侧边，用于展示主要功能层级并在不同页面间切换的导航区域。 | 不等同于展示补充内容的普通侧栏或临时抽屉。 |
| 页面标题区 | Page Header | 展示当前页面名称、说明、状态和页面级主要操作的区域。 | 不等同于全局顶部栏；其内容随当前页面变化。 |
| 主内容区 | Main Content | 承载当前页面核心信息和主要任务的页面区域。 | 一个页面通常只有一个语义上的主内容区。 |
| 侧栏 | Sidebar | 位于主内容区侧边，承载补充信息、辅助导航或上下文操作的常驻区域。 | 不等同于侧边导航；侧栏通常服务当前页面内容。 |
| 筛选区 | Filter Area | 集中放置搜索和筛选条件、用于缩小当前数据范围的页面区域。 | 应说明默认条件、展开收起方式和重置行为。 |
| 操作区 | Action Area | 集中放置创建、编辑、导入、导出或批量处理等业务操作的区域。 | 强调业务动作，不等同于用于排版控件的普通工具栏。 |
| 工具栏 | Toolbar | 将一组相关按钮、菜单、切换器等控件集中排列的区域。 | 工具栏描述控件容器，不自动说明其中操作的业务优先级。 |
| 概览区 | Summary Area | 汇总当前对象或页面的关键状态、指标和重要信息的区域。 | 不等同于完整数据看板；通常服务当前页面或对象。 |
| 内容区块 | Content Section | 按主题组织一组相关内容或操作的页面区域。 | 区块是信息分组，不必拥有独立页面或业务生命周期。 |
| 卡片 | Card | 将一组相关信息和操作组织成独立视觉单元的内容容器。 | 卡片是呈现方式，不应直接作为业务对象名称。 |
| 数据表格 | Data Table | 以行列结构展示同类对象及字段，并可承载选择、排序和行操作的组件区域。 | 不等同于只展示静态内容的普通表格；交互能力应按需求明确。 |
| 详情信息区 | Detail Section | 按分组展示单个业务对象属性、状态和关联信息的区域。 | 不等同于整个详情页；一个详情页可以包含多个详情信息区。 |
| 固定操作栏 | Sticky Action Bar | 在页面滚动时保持可见，用于承载需要持续可达的关键操作区域。 | 是否固定、固定位置及遮挡处理需要明确。 |
| 页面底部 | Page Footer | 位于页面末尾，承载辅助链接、版权、补充说明或次要操作的区域。 | 不应放置完成核心任务所必需但不易发现的操作。 |

## 常见控件与展示组件

| 标准术语 | 英文 / 缩写 | 定义 | 使用边界与易混概念 |
|---|---|---|---|
| 按钮 | Button | 用户点击或触发后执行明确操作的控件。 | 按钮执行动作；跳转到其他位置通常优先使用链接。 |
| 主要按钮 | Primary Button | 在当前页面或任务中代表最主要推荐操作的按钮。 | 同一任务区域通常只突出一个主要操作，不能把所有按钮都设为主要按钮。 |
| 次要按钮 | Secondary Button | 承载非主要但仍需明显提供的辅助操作按钮。 | 与主要按钮的区别是任务优先级，不是能否点击。 |
| 图标按钮 | Icon Button | 主要通过图标表达操作的按钮。 | 图标含义不明显时应提供可访问名称或提示说明。 |
| 链接 | Link | 将用户导航到另一个页面、位置或外部资源的可操作文本或元素。 | 链接负责导航，按钮负责执行操作；不要只按视觉样式区分。 |
| 文本输入框 | Text Field | 接收单行文本输入的控件。 | 应明确标签、格式、长度、必填性、默认值和校验反馈。 |
| 多行文本框 | Text Area | 接收较长或多行文本输入的控件。 | 不等同于富文本编辑器；是否支持格式需要单独说明。 |
| 数字输入框 | Number Input | 接收数值并可限制范围、精度或步长的输入控件。 | 不应仅依赖输入框类型表达单位和业务范围。 |
| 下拉选择器 | Select | 从预定义选项中选择一个或多个值的控件。 | 选项较少且需要同时可见时，可使用单选框或复选框。 |
| 级联选择器 | Cascader | 按层级逐级选择关联选项的控件。 | 适用于层级关系，不适合无层级的普通多选。 |
| 单选框 | Radio Button | 从一组互斥且通常同时可见的选项中选择一个值的控件。 | 用户必须理解全部选项时优于下拉选择器。 |
| 复选框 | Checkbox | 独立开启或关闭一个选项，或从一组选项中选择多个值的控件。 | 不等同于立即改变系统状态的开关。 |
| 开关 | Switch | 在两个即时生效的相反状态之间切换的控件。 | 适合启用/停用等立即生效设置；需要提交表单时通常使用复选框。 |
| 日期选择器 | Date Picker | 帮助用户选择单个日期或日期范围的控件。 | 应明确时区、可选范围、日期格式及是否包含时间。 |
| 时间选择器 | Time Picker | 帮助用户选择时间点或时间范围的控件。 | 应明确时区、精度及跨日规则。 |
| 文件上传 | File Upload | 选择并提交本地文件或外部文件的控件。 | 应明确类型、大小、数量、上传进度、失败处理和删除规则。 |
| 菜单 | Menu | 展示一组可选择命令或导航项的控件。 | 菜单项应是操作或去向，不应把大段正文放入菜单。 |
| 下拉菜单 | Dropdown Menu | 由按钮或其他触发器展开的一组临时操作或选项。 | 不等同于用于填写表单值的下拉选择器。 |
| 树形控件 | Tree View | 按父子层级展示并允许展开、收起或选择节点的组件。 | 用于层级数据，不应把无层级列表强行组织成树。 |
| 穿梭框 | Transfer List | 在两个列表间移动条目，用于批量选择或分配对象的控件。 | 适合可选项较多且需要比较已选与未选集合的场景。 |
| 步骤条 | Stepper | 展示多步骤任务的当前进度、已完成步骤和后续步骤的组件。 | 不等同于进度条；步骤条表达离散阶段。 |
| 进度条 | Progress Bar | 展示任务完成比例或处理进度的组件。 | 无法确定完成比例时应使用不定进度状态，不能显示虚假百分比。 |
| 状态标签 | Status Tag | 用短文本和视觉样式标识对象分类或当前状态的组件。 | 颜色不能作为唯一信息来源；标签名称必须沿用业务状态定义。 |
| 徽标 | Badge | 用数字、圆点或简短标记提示数量、更新或需要关注状态的组件。 | 适合辅助提醒，不应独立承载复杂业务含义。 |
| 头像 | Avatar | 用图片、文字或图标代表用户、组织或其他主体的组件。 | 头像是身份识别辅助，不替代主体名称。 |
| 富文本编辑器 | Rich Text Editor | 支持文本格式、链接、图片等内容编辑能力的输入组件。 | 应明确支持的格式、粘贴规则、内容限制和最终展示效果。 |
| 评分控件 | Rating | 通过星级、分值或等级收集评价的控件。 | 应明确量表范围、含义、是否允许修改和是否匿名。 |

## 账号、组织与权限

| 标准术语 | 英文 / 缩写 | 定义 | 使用边界与易混概念 |
|---|---|---|---|
| 用户 | User | 实际使用产品完成任务的人。 | 不等同于系统中的登录账号；一人可能拥有多个账号。 |
| 账号 | Account | 用户用于识别身份、登录并承载产品权益或配置的系统记录。 | “账户”容易与资金账户混淆；非财务场景优先使用“账号”。 |
| 成员 | Member | 已加入某个组织、团队或空间，并在其中获得身份与权限的用户。 | 用户是全局概念，成员是特定协作范围内的身份。 |
| 组织 | Organization | 对成员、资源、权限和业务归属进行统一管理的协作主体。 | 不一定等同于现实中的法人公司。 |
| 团队 | Team | 组织内按协作目标形成的成员分组。 | 是否能独立拥有资源和权限，应由产品规则明确。 |
| 租户 | Tenant | 在多租户产品中拥有相对独立数据、配置和权限边界的客户实例。 | 不自动等同于组织；一个客户或组织是否对应一个租户需单独定义。 |
| 工作空间 | Workspace | 围绕项目或协作目标组织成员、内容和配置的产品空间。 | 不同产品中可能位于组织之下或独立存在，必须说明归属关系。 |
| 角色 | Role | 对一组职责或权限的命名集合。 | 角色不是具体用户，也不等同于职位。 |
| 权限 | Permission | 允许某个主体对特定资源执行特定操作的规则。 | 应描述“谁、对什么、能做什么”，不能只写“有权限”。 |
| 管理员 | Administrator | 在特定范围内拥有成员、权限、配置或资源管理职责的角色。 | 必须注明管理范围，例如系统管理员、组织管理员或项目管理员。 |
| 所有者 | Owner | 对某个组织、空间、项目或业务对象承担最高管理责任的成员角色。 | 不必然拥有系统级权限；所有权能否转移需由产品规则定义。 |
| 身份认证 | Authentication | 验证用户或其他主体是否为其所声明身份的过程。 | 回答“你是谁”，不等同于判断可以执行什么操作。 |
| 授权 | Authorization | 根据身份、角色和规则决定主体能够访问哪些资源、执行哪些操作的过程。 | 回答“你能做什么”，不等同于身份认证。 |
| 注册 | Sign-up / Registration | 用户创建新账号或建立产品身份的过程。 | 不等同于登录、加入组织或完成首次使用引导。 |
| 登录 | Sign-in | 用户通过身份认证进入其账号或产品会话的过程。 | 不等同于授权；登录成功不代表拥有全部功能权限。 |
| 退出登录 | Sign-out | 用户主动结束当前登录会话的操作。 | 不等同于注销账号或退出组织。 |
| 邀请 | Invitation | 已有成员向其他人发出加入组织、团队或空间的请求。 | 应明确邀请有效期、目标角色、重复邀请和撤回规则。 |

## 内容、状态与通用操作

| 标准术语 | 英文 / 缩写 | 定义 | 使用边界与易混概念 |
|---|---|---|---|
| 草稿 | Draft | 内容已保存但尚未正式对目标用户生效或可见的状态。 | 草稿是否可协作、可预览和自动保存，需要单独说明。 |
| 发布 | Publish | 使内容或配置从未生效状态进入目标范围可见或可用状态的动作。 | 不等同于部署；发布面向业务可见性，部署面向软件运行版本。 |
| 下架 | Unpublish / Take Down | 使已发布内容停止对目标范围展示或生效的动作。 | 通常保留内容和历史记录，不等同于删除。 |
| 归档 | Archive | 将低频或已结束对象从主要工作区移出，同时保留记录和可追溯性的动作。 | 不等同于删除；是否允许恢复需要明确。 |
| 删除 | Delete | 使对象从正常使用范围移除的动作。 | 应明确是可恢复删除还是永久删除，以及关联数据如何处理。 |
| 启用 | Enable | 使某项能力、配置或对象进入可被使用的状态。 | 不等同于发布；启用可以作用于已经存在但被关闭的对象。 |
| 停用 | Disable | 阻止某项能力、配置或对象继续被使用，同时通常保留数据。 | 不等同于删除或下架。 |
| 审核 | Review / Moderation | 对内容、资质或申请是否符合既定规则进行判断的业务动作。 | 与审批不同：审核强调核验规则，审批通常包含授权决策。 |
| 审批 | Approval | 由具有授权职责的角色决定申请是否可以继续或生效的业务动作。 | 不要与审核、评审混用。 |
| 撤回 | Withdraw | 发起人在流程完成前主动收回已提交事项的动作。 | 不等同于撤销；撤销通常作用于已经生效的结果。 |
| 撤销 | Revoke / Undo | 取消已执行动作或已生效结果的业务效果。 | 是否恢复到前一状态、是否保留历史，必须明确。 |
| 操作记录 | Activity Log | 记录用户对业务对象执行过哪些关键操作的可查看历史。 | 面向业务追溯；不等同于面向研发排障的系统日志。 |
| 导入 | Import | 将外部文件或数据批量写入产品的能力。 | 应明确格式、校验、重复处理、失败反馈和回滚规则。 |
| 导出 | Export | 将产品中的数据按权限和范围生成外部文件的能力。 | 应明确字段、格式、数据范围、时效和敏感信息处理。 |
| 批量操作 | Bulk Action | 对多个已选择对象一次执行同类操作的能力。 | 应明确选择范围、部分失败处理和二次确认规则。 |
| 通知 | Notification | 产品因事件或状态变化向用户传递信息的机制。 | 站内信、短信、邮件和推送是不同渠道，不应笼统等同。 |

## 不纳入核心表的协作术语

以下概念可能出现在跨职能协作中，但不属于本表的核心产品术语：高层设计（HLD）、低层设计（LLD）、接口契约（API Contract）、防腐层（ACL）、架构决策记录（ADR）、测试策略、测试规格、严重度、运行手册（Runbook）和需求追溯矩阵（RTM）。它们应由相应的技术设计、测试或交付规范定义。
