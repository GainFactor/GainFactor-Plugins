# 中文产品语言规范

本规范用于让中文 PRD 对产品、业务、设计、研发和测试读者都能直接理解。它约束正文表达，不改变已确认的产品范围、业务规则、状态、优先级、验收标准或稳定标识。

## 产物分层

同一个概念进入不同产物时，应按读者任务选择表达方式：

| 内容层级 | 主要读者 | 表达要求 |
|---|---|---|
| PRD 正文 | 产品、业务、设计、研发、测试 | 使用具体的产品、页面、业务对象、信息来源、用户操作和页面反馈 |
| 按需附录 | 评审者、负责人 | 保留调研依据、现有能力差距、详细术语、依赖分析、项目计划和资源安排 |
| 工作过程 | 写作者 | 保存扫描、资料筛选、分析和检查记录；不作为正式 PRD 章节 |
| 领域模型 | 业务专家、产品、研发 | 可以使用共同语言、模型边界、业务不变量和领域事件等领域术语 |
| 验收标准 | 产品、测试、研发 | 使用可观察、可判定的条件和结果，不依赖读者推断 |
| 技术设计 | 研发、架构师 | 可以使用接口、组件、存储、事件和部署等技术语言 |
| `TRACEABILITY-METADATA` | 工具与下游文档 | 保持英文键名、枚举值、稳定 ID 和关系类型不变 |

领域模型是业务规则的来源，不是 PRD 句式模板。复用领域模型时保留已确认含义，但应将其翻译成目标读者能够识别的产品语言。

“上下文收集报告”和完整的“相关能力识别”默认属于工作过程。相关结论影响产品范围或决策时，在正文写清结论和影响；评审需要查看完整依据时，将材料放入附录。

## 写清语义角色

关键需求应让读者识别主体、动作、对象、条件和结果。必要时继续说明页面反馈、对象状态或失败后的恢复方式。

这是一项完整性检查，不要求机械套用固定句式。缺少某个角色但不影响理解时可以省略；存在多种合理解释时必须补全。

优先从用户或业务参与方开始描述。确实由自动任务或外部事件触发时，应写明触发来源、适用条件和相关方能够观察到的结果，避免只写“系统进行处理”。

## 先确定名称层级

写需求前先确认下列层级，避免用抽象能力名称代替产品界面：

```text
产品或系统 → 使用端 → 页面 → 功能模块 → 业务对象 → 用户操作 → 状态或结果
```

- 产品或系统：用户认为自己正在使用的完整产品。
- 使用端：前台网站、移动端、管理后台、运营后台、商家后台或其他明确端形态。
- 页面：用户能够进入并识别的页面，例如列表页、详情页、编辑页。
- 功能模块：页面内承担一组相关任务的区域。
- 业务对象：用户实际查看或操作的内容，例如订单、成员、内容、申请。
- 用户操作：搜索、筛选、创建、提交、审核、发布等可执行动作。
- 状态或结果：操作后对象、页面或流程发生的可观察变化。

同一名称在多个层级都可能成立时，正文应补足限定词。不要只写“系统”“平台”“对象”“内容”或“结果”，除非上下文已经唯一确定其所指。

## 页面需求的基本表达

涉及界面的功能需求通常应让读者看出四件事：

1. 在什么情况下；
2. 页面展示什么；
3. 用户可以执行什么操作；
4. 操作后页面或业务对象如何变化。

这四项是信息检查项，不要求每句话机械套用同一个句式。可以合并或拆分，但不能省略会改变实现或验收理解的关键条件与结果。

示例：

> 当列表中没有符合当前搜索和筛选条件的内容时，页面显示空状态，并保留已输入的关键词和筛选条件。用户可以修改条件或清空筛选，页面随后按新条件重新展示结果。

## 将抽象表达落到产品事实

以下词并非绝对禁用，但在 PRD 正文中出现时，应检查是否掩盖了具体产品含义：

| 抽象表达类型 | 常见信号 | 应补充或改写为 |
|---|---|---|
| 泛化主体 | 系统、平台、当前对象 | 明确的产品、使用端、页面或业务对象 |
| 泛化信息 | 原始信息、当前事实、系统内容 | 具体字段、内容类型或信息来源 |
| 泛化动作 | 获得、取得、形成、消费、处理 | 用户或系统实际执行的业务动作 |
| 泛化结果 | 用户看到的结果、结果范围、对象变化 | 页面展示内容、对象状态或后续可执行操作 |
| 泛化入口 | 操作入口、调整入口、访问入口 | 按钮、链接、菜单、页面或具体操作；无需定义控件时至少写明动作 |
| 逻辑化修饰 | 条件化展示、关联层级消失 | 明确触发条件，以及展示、隐藏或禁用的具体内容 |
| 流程标签 | 进入某旅程、消费某流程 | 用户开始的任务、执行的步骤或进入的页面 |

改写时不得根据词面机械替换。先确认原句中的主体、条件、对象、来源、动作和结果；缺少证据且不同解释会改变产品行为时，标记为“需要产品确认”。

## 信息来源必须具体

当信息来源影响可信度、展示规则、刷新方式或验收结果时，正文应明确来源类型，例如：

- 用户填写的信息；
- 业务人员维护的信息；
- 第三方平台提供的信息；
- 产品根据已批准规则生成的信息；
- 历史业务记录。

不要用“事实来源”“原始数据”“系统数据”等笼统名称代替已知来源。若来源不影响产品行为，可避免在每句话中重复，以免正文变成数据血缘说明。

## 正文与精确契约的边界

- 正文先保证业务读者能够理解，再用稳定 ID、规则表或验收标准承载精确追溯。
- 不把 `REQ-*`、`FLOW-*`、关系类型或 metadata 字段拼进自然语言句子。
- 页面名称采用用户与产品团队能够识别的名称；领域能力名称可作为背景或范围说明，但不默认充当页面或使用端名称。
- 业务状态必须沿用已批准定义；可以优化状态说明，不能为了语言自然擅自合并、重命名或改变状态机。
- 验收标准可以比正文更精确，但仍应写成产品经理能够判断的可观察结果。

## Writer 自检

完成中文 PRD 后，至少检查：

- 不阅读领域模型，是否仍能判断当前描述的是哪个产品、使用端和页面？
- 每个页面模块展示什么、何时展示、可以执行什么操作，是否清楚？
- “系统、对象、内容、信息、结果、入口”等泛称是否有唯一指代？
- 信息来源影响产品规则时，是否写明具体来源类型？
- 是否把领域建模、技术设计、追溯或测试语言直接写进了产品正文？
- 每项关键需求是否能识别主体、动作、对象、条件和结果？
- 上下文扫描、能力分析过程和审查记录是否被留在正文之外？
- 改写是否保持业务含义、稳定 ID 和已批准规则不变？

## Reviewer 门禁

Reviewer 除结构、逻辑、追溯和可测试性外，还应独立检查正文可读性：

- 一名未阅读领域模型的产品经理能否识别产品端、页面、功能、展示条件、信息来源、用户操作和操作结果？
- 页面或系统是否被抽象能力名称替代，导致读者无法判断真实产品形态？
- 抽象名词或名词化动词是否造成多种合理解释？
- 正文是否需要依赖 metadata、领域模型或技术文档才能理解基本产品行为？
- 正文是否混入执行过程或治理说明，完整依据是否被放在合适的附录中？
- 是否结合段落用途判断问题，而非仅凭一个抽象词或术语报错？

局部措辞生硬但含义唯一，可按现有分级记录为表达改进；若问题系统性出现、造成需求边界或产品行为无法独立理解，应按需求清晰度问题处理，不能仅因 `trace-lint`、构建或视觉门禁通过而准出。
